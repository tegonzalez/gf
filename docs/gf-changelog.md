# git-folders Changelog

## Unreleased

### User-facing behavior

- `gf clone <url>` now accepts a single URL, derives the name and path from it, and supports `-n` and `-b`.
- Bare host/path URLs like `github.com/cursor/plugins` are expanded to `https://`.
- `gf ls` and `gf status` display the git-folder `url` in the second column and align columns generically.
- `gf clone` and `gf pull` now create a local tracking branch for branch/default-branch refs instead of a detached `HEAD`.
- `gf pull` skips local placeholder URLs from `gf init`.
- A `url` naming a folder inside a repository creates a subfolder binding: `gf` resolves where the repository ends (remote URLs probed by longest `git ls-remote` prefix, local paths by walking up) or reports an error that tells the user to write `.git` after the repository name — the hint reaches the CLI.
- Subfolder bindings share one bare repo store per repository and sparse linked worktrees under `<root>/.gf`; a relative symlink at the consumer path shows only the mapped folder.
- Pinned refs get collision-free `ref=` checkout keys: a branch named `ref=<x>` cannot collide with tag or commit `x`.
- `gf status`, `gf ls`, and drift are scoped per binding to the mapped folder and stay local-only.
- `gf pull` groups subfolder bindings by repo store and checkout — one fetch per store — and marks bindings moved along with another.
- `gf rm` removes only the consumer link and manifest entry; adding the binding back restores the folder with its uncommitted work.
- `gf worktree add` links to the source consumer path, so later retargets propagate link to link.
- `gf diff` and `gf log` scope to the binding's folder by default (`-- .` appended when no pathspec is given).
- Errors while handling an identified git-folder carry the folder name, path, and operation.
- `gf ls`, `gf status`, and `gf status --remote` handle a git-folder child with no commits: it is listed with `[]` for branch and `?` in the short-hash column (plus `*` when it has uncommitted changes) and its porcelain lines under `status`, without failing or hiding the other bindings; `gf status --remote` gives the deterministic unresolvable-ref error, or reports `behind`/`both` when the ref resolves locally, instead of a raw git error.
- `gf pull` refuses a subfolder binding whose changed `url` resolves to a whole repository — the error names the binding and says the switch is not supported, the command exits `1`, and nothing changes (no selected binding is updated); and `gf pull` no longer re-probes the `url` of an established whole-repo child — the resolution recorded in `.gf/state` stands.
- `gf clone` of a subfolder binding now fetches a joined repo store before resolving the ref (a newer tag or branch cloned second now works), and a failed first clone no longer leaves behind a repo store it created.
- `gf clone --depth <n>` of a subfolder binding now creates a shallow repo store — the depth is passed to the store's fetch instead of silently producing a full-depth store.
- An unusable `gf -C <path>` — including a dangling consumer link — now fails cleanly with `gf: cannot change to '<path>': <reason>` and exit `1`, instead of a Python traceback.
- Per-checkout state records moved out of the checkout-key namespace (`wt/<rk>/.<key>.state`), so a branch or ref named `<existing-key>.state` no longer collides with an existing checkout's state file — e.g. cloning `master.state` alongside `master` now works in either order instead of dying with a misleading error or a traceback.
- `gf pull` on a selected subfolder binding whose consumer path is not yet a link (missing path, `gf init` placeholder, fresh checkout) now goes through the grouped pull — one fetch per store and the fetched ref applied — instead of fetching per binding and printing `Pulled` without updating files.
- `gf clone` of a subfolder inside a local `gf` whole-repo child now records the child's inner gitdir (`.gf/git`) as the store's `remote.origin.url`, so the clone and later `gf pull` fetches work — previously the child directory itself was recorded and the fetch died with "does not appear to be a git repository".
- `gf pull` now rebuilds missing `.gf` store and checkout storage for selected subfolder bindings whose consumer links survived — previously it died with a raw `git config remote.origin.url` error and could never recover.
- `gf pull` run inside a `gf worktree add` worktree now updates the source shared checkout through the link chain — the added worktree no longer grows its own `.gf` store or has its consumer link retargeted away from the source; previously the pull silently split storage and left the source stale.
- When a `gf pull` spans multiple repo stores and a later store's fetch or setup fails, the error now names a binding of that store — and the `Pulled` lines for bindings that already succeeded still print — instead of blaming the first selected binding.
- Cloning onto a path that is already a consumer link now binds or refuses by the lexical consumer path — the manifest never records the resolved `.gf/wt/...` storage path, which previously defeated duplicate-path detection and let a later `gf rm` corrupt the shared worktree; `gf init <path>` received the same leaf-literal treatment — its error envelope spells the consumer path and it refuses a leaf link that resolves outside the parent; and `gf rm` refuses any manifest path spelling `.gf/` interior.
- `gf pull` with a `latest` binding on a `--single-branch` store now probes the remote's default branch once, records fetch coverage for it, and repoints `origin/HEAD` — previously the pull died `could not resolve ref 'latest'`.
- `gf status`, `gf ls`, and `gf status --remote` no longer abort on a subfolder binding whose checkout directory was deleted — `status --remote` reports it as `missing` and all three keep listing its siblings — previously they died with a raw `this operation must be run in a work tree` error.
- `gf clone` of a subdirectory whose name has glob characters (`app/[id]`) or begins with `--` now works: sparse-checkout operands are passed literally after `--`, with `--skip-checks` added only when a member needs it (git ≥ 2.36; the flag is dropped on retry for older git).
- Repo-boundary detection no longer mistakes a directory containing an ordinary file named `HEAD` for a bare repository — a repository tracking e.g. `docs/HEAD` previously made the local ancestor walk resolve `docs/` as the repo URL, so `gf clone` of a path under it — or a later `gf pull` of a binding whose recorded local url names it — failed the store fetch or bound the wrong upstream; both detection sites now share one `_is_bare_repo_dir` predicate requiring the real triad — a `HEAD` file plus `objects/` and `refs/` directories.
- Rollback after a failed `git worktree add` no longer deletes the wrong admin record — git creates `<key>1` when `<store>/worktrees/<key>` is already occupied, but rollback unconditionally removed `worktrees/<key>`, destroying a pre-existing foreign worktree record and leaking `<key>1` (`_remove_checkout` had the same wrong-target removal); a shared `_checkout_record_dir` now resolves the record the call actually created — read from the new checkout's `.git` `gitdir:` line, verified to sit inside the store's records dir — and both rollback sites remove only that record, so foreign worktrees stay intact and usable.
- Scoped status no longer mis-reads a bound directory whose name carries pathspec magic — a recorded subdir spelled `:(literal)foo` previously reached `git status --porcelain -- <paths>` raw and matched a different directory (dirty files reported clean, the pull dirty guard bypassed), while `*`/`[x]` names over-matched into sibling paths; `scoped_porcelain` now runs with `GIT_LITERAL_PATHSPECS=1`, so `gf status`, `gf ls`, and `gf status --remote` all see recorded paths literally.
- A subfolder binding's pull dirty check no longer misses dirt outside the mapped subdirs — it scoped `status --porcelain` to the binding's union cone, so a dirty cone-materialized root or ancestor file stayed invisible and an unforced pull proceeded over local changes while `--rebase --autostash` skipped the stash and died inside rebase; the check now runs unscoped over the whole materialized checkout — skip-worktree still confines the report to cone content, and physically-present untracked files count exactly as a whole-repo child's — with `--force`/`--autostash` semantics unchanged.
- A shared checkout's state now records each served binding's effective `url` in a `binding_urls` map keyed by manifest `path` — the scalar `url` stays written last-writer-wins across the bindings the checkout serves for compatibility, but the pull lookup no longer reads it — a sibling spelled differently but resolving to the same store (e.g. a remote `…/upstream` spelling vs `…/upstream.git`, which share one store because `repo_key` strips `.git` for remote spellings — local `repo` and `repo.git` paths are distinct) previously mismatched on every pull and paid repeated `ls-remote` re-resolution; `gf pull` now compares the binding's url against its own map entry and takes `repo_url` from the store's `remote.origin.url` only when that origin still keys this store, so a `gf`-child inner-gitdir origin can't route the binding to a phantom store.
- `gf clone <url> missing/..` — and `gf init` of a `.`/`..` leaf — no longer plants a child inside an existing directory: the leaf stayed literal, so the occupancy check stat'd through a nonexistent intermediate and missed that the destination was the parent repository itself — the clone planted `.gf/git` at the parent root and a failed fetch's cleanup recursively deleted the parent's contents, `.git` included; a `.`/`..` leaf now resolves to the real directory before containment and occupancy (`missing/..` is refused as the already-existing parent, `missing/../..` hits containment), the recorded manifest `path`/`name` use the resolved spelling, and clone cleanup additionally refuses to remove a child that resolves to the parent root.
- `gf log --oneline x.txt` and `gf diff x.txt` inside a subfolder binding no longer die `fatal: bad revision 'x.txt'` — `-- .` was appended whenever no `--` appeared, forcing the operand into revision position even though the contract lets any pathspec disable the scope; a trailing non-dash operand that names an existing path under the mapped directory or carries pathspec magic (`*`, `?`, `[`, leading `:`) now suppresses the default scope — an option value that coincidentally names an existing path or glob suppresses it too, so `gf <cmd> -- <paths>` remains the exact escape.
- A failed `gf pull` that had just created a shared repo store no longer leaves that store behind: the store-phase failure path removed nothing, so a first `pull` aborted mid-fetch left the half-created store and a retry then failed with `'master' is already used by worktree` — `pull` now removes a repo store on store-creation/initial-fetch failure only when the pull itself created it, never a pre-existing or already-serving store.
- `gf status`, `gf pull`, and `gf rm` invoked with no path arguments from a physical shared-checkout directory (`cd -P` into `.gf/wt/<repo-key>/<checkout>` or a subdirectory) now select the bindings their location implies: the synthesized operand was spelled relative to the parent root, so from inside the checkout it re-anchored to a nonexistent path and selected nothing — silently empty `status`, a no-op `pull`, an unacted `rm`. Separately, a `gf` command run from inside `.gf/wt` could previously mis-scope the sparse cone — `sparse-checkout set` resolved its operands against the process cwd rather than the checkout root and could rewrite the cone to nonexistent paths, dangling every consumer link; cone operands are now pinned to the checkout root.
- `gf status --remote` now reports a subfolder binding whose mapped directory disappeared from its checkout as `missing` — an upstream update that removes the directory leaves `gf pull` succeeding and the consumer link dangling, but drift tested only the checkout root and reported `clean`; drift now treats a dangling consumer link (mapped subdirectory absent from the checkout) like an absent one, while `gf status` and `gf ls` keep listing the binding's siblings.
- `gf clone` no longer fails for a mapped subdirectory whose name contains `!`: the `sparse-checkout set --cone` invocation already suppressed git's cone validation for glob-like names but not for a `!` name, which git rejects as a pattern-like operand — the validation is now skipped for `!`-bearing operands too, so `!foo` or `app/!foo` mappings clone cleanly (supersedes the GF-TRB-9 known issue).
- `gf clone` of a local path that resolves inside another parent's `.gf` no longer binds the parent's private storage as a subfolder — `gf clone <other-parent>/<consumer-link> <path>` resolved through the link into `.gf/wt/...`, found no repository boundary (`gf` removes the checkout's `.git` gitfile by design), climbed to the source parent's `.git`, and bound the source parent as the repo URL with `.gf/wt/...` as the subdir — exit `0` with a permanently dangling consumer link; local-path resolution now refuses targets inside a `.gf` directory — `gf`'s private layout — with a clear error naming it, while leaf-as-boundary spellings (`.gf/repos/<repo-key>/git`, `<child>/.gf/git`) still self-resolve, and remote URLs containing `.gf/` are untouched since they resolve against the remote tree.
- `gf clone`, `gf init`, and `gf worktree add` now refuse a spelled target that resolves inside the parent's `.gf` storage — after `gf clone <up>/docs vendor/docs`, a follow-up `gf clone <up> vendor/docs/nested` resolved through the ancestor consumer link into `<checkout>/docs`, passed containment, hit the already-initialized shortcut, and exited `0` with a manifest `path` pointing into `.gf/wt` that `gf rm` then refuses; `gf init` created the directory inside the managed checkout before failing, and `gf worktree add` could plant the new worktree there. Each now fails with a clear error instead; re-adding an existing consumer link itself is unaffected.
- Path arguments now select a binding by its spelled consumer path before realpath matching — `gf clone <up>/docs one` plus `gf clone <up>/docs two` gave two bindings sharing one realpath and one map depth, so the realpath-only match selected both: `gf rm one` removed both links and both manifest entries, and `gf status`, `gf ls`, and `gf pull` over-selected the same way; an operand spelling a consumer path selects that binding by its path (innermost wins), realpath matching remains the fallback for operands inside a consumer link or spelled physically, and a physical operand naming the shared map itself still selects every aliased binding.
- A `tag` or `commit` ref on a subfolder clone that creates the repo store is now covered like a join: `gf clone <up>/docs -b v1 --depth 1` failed `could not resolve ref 'v1'` when the tag's commit predated the shallow tip, and an orphan tag failed on any fresh store, because the creating fetch carried only the branch-or-wildcard refspec; `_ensure_pinned_ref` now runs on the create arm before the store's initial fetch, so a needed tag's `+refs/tags/<ref>:refs/tags/<ref>` line is appended in time to land in that one fetch, while a pinned commit sha gets the supplemental `git fetch origin <sha>` — sent without `--depth` (an arbitrary-sha fetch needs the server to allow it). The `--single-branch` narrowing write is now coverage-aware too — it no longer dies `cannot overwrite multiple values` when a pin's tag line already sits on the key.
- A `tag` or `commit` binding joining a `--single-branch` repo store no longer fails `could not resolve ref '<ref>'` — the join fetch kept the store's branch-only refspec, and git's tag auto-following only delivers tags that point into fetched history, so a pinned ref outside that history never reached the store (the same hole hit the pull coverage loop and whole-repo children, where a narrowed child gitdir or a `ref=` override could pin an unfetched tag or commit); a shared `_ensure_pinned_ref` now probes the store for the tag or commit first and, on a miss, probes upstream (`ls-remote` for tags) and appends `+refs/tags/<ref>:refs/tags/<ref>` — append-only, so the same single fetch lands it — while a bare commit sha gets a one-shot `git fetch origin <sha>`, existing refspec lines are never rewritten, and `could not resolve ref` still covers genuinely-absent refs.
- `gf pull` invoked through a `gf worktree add` worktree at a different directory depth no longer mis-resolves a binding's relative `url` — a source-relative spelling like `../producer/child/docs/api` was absolutized against the invoking worktree (`nested/wt2`), so `../producer` landed outside the workspace; the recorded-resolution guard correctly rejected the stored `.gf/git` origin, but the re-resolution ran on the already-mis-anchored `url`, the local walk-up bound the wrong tree, and the pull retargeted the source parent's consumer link to a nonexistent folder while still printing `Pulled`. `gf pull` now resolves the binding's checkout first and anchors a relative `url` at the root that owns the binding's links and `.gf` storage — the source root for `worktree add` link chains — so an unchanged `url` resolves identically from any worktree.
- Path operands carrying `.`/`..` segments now select the same bindings as their normalized spelling — `gf status sub/../vendor` selected nothing where `vendor` selects `vendor/api`: the operand reached `_below` unnormalized, so its lexical containment arm never saw `vendor/api` as below `sub/../vendor`, and its realpath arm compared the hidden checkout map against the operand's resolved parent dir; `gf pull`, `gf ls`, and `gf rm` skipped the same bindings the same way. The below-target comparison now normalizes the operand — `.`/`..` segments resolve by directory identity — while a spelled operand that traverses a consumer link mid-path still resolves by realpath.
- Subfolder checkouts materialize with `sparse-checkout --cone`: cone mode checks out each mapped subdirectory's full tree plus files at the repository root and directly inside each ancestor directory of a mapped subdirectory, while unmapped directory trees stay filtered — a same-named directory at another depth is not materialized. "Exposes only the mapped subdirectory" remains a property of the consumer link, not of the hidden checkout's contents.
- `gf worktree add <path> <commit-ish>` emitted its positionals to `git worktree add` in reverse — the commit-ish landed in the path slot and the resolved `<path>` in the ref slot, so git rejected every explicit commit-ish with `fatal: invalid reference` (a bare `gf worktree add <path>` was unaffected); the positionals now emit `<path>` then `<commit-ish>`, matching the documented signature.
- `gf worktree add` no longer leaves a registered-but-unlinked worktree behind when a child path already exists in the new worktree: `gf init vendor/zz` over tracked content materializes a real `vendor/zz/` directory at the child path, where the link phase previously died after `git worktree add` had already registered the worktree — a retry hit the same wall until the orphan was removed by hand — and under `-f` the same collision crashed `IsADirectoryError` on the directory's `unlink`. The post-add phase now rolls the just-created worktree back with `git worktree remove --force` when a later step fails, and a real directory at a child path is refused even under `-f` — only a link or file is replaced.
- `gf init` no longer creates the child's `.gf` before checking the manifest for name/path collisions: `gf init kid2 -n dup` made `kid2/` and `kid2/.gf/git`, then died `git-folder 'dup' already exists in manifest` — and the corrected retry died `kid2 already has a .gf directory` on the half-made child. All validation — containment, `.gf`-storage and `.git`/`.gf` occupancy, and the manifest name/path collision checks — now runs before any directory or `.gf` is created, matching the validate-then-create order `gf clone` already used.
- `gf pull` anchors a binding's relative `url` by declared-path identity — the root under which the binding's declared `path` resolves to its checkout — instead of the nearest `.git` ancestor of the child: the whole-repo fallback walked `.git` ancestors from `child.parent` and stopped at ANY of them, so an unrelated `git init` at `p/nested`, sitting between the child `p/nested/child` and the manifest-owning root `p`, claimed the anchor — `../dep3` re-resolved against `p/nested` as `p/dep3`, the bogus `remote.origin.url` persisted into the child's `.gf/git`, a same-named repository turned the pull into a silent `checkout -B` onto foreign history, and a `gf init nested/child` placeholder resolved into a permanently dangling link. The anchor is `owning_root` first for a store checkout, then the root under which the declared `path` resolves to the checkout, with the invoking root as fallback — a foreign nested repository cannot claim it.
- `gf worktree add` no longer writes the copied manifest through a checked-out symlink: a commit whose tree contains `gf.toml` (or `gf.local.toml`) as a symlink materializes the link in the new worktree, and the manifest copy's `write_text` followed it — the parent's manifest content landed at the link's target outside the new worktree, so a committed `gf.toml -> /abs/path` was an arbitrary-file overwrite. A checked-out symlink at the manifest destination is now unlinked and replaced by a regular file, and a non-regular, non-symlink destination — e.g. a committed `gf.toml/` directory — is refused, rolling the new worktree back per the add-failure contract.
- `gf clone` of a relative local path invoked from a subdirectory no longer fetches at the wrong anchor: the binding's resolution anchored the spelled `url` at the parent root, but the new child's `origin` and its fetch used the raw spelling anchored at the process cwd, so `cd parent/sub && gf clone ../upstream.git kid` failed `does not appear to be a git repository` — or, when a same-named repository was reachable under `parent/sub`, cloned the wrong repository — while the manifest recorded the parent-relative spelling every later pull resolves correctly. `init_child` now feeds the anchored `repo_url` to `origin` and the fetch, matching `ensure_repo_store`; the manifest still records the spelled url.
- `gf pull` invoked through a `gf worktree add` worktree no longer prunes bindings missing from that worktree's manifest copy: `worktree add` snapshots the manifests at add time, so a binding added to the source manifest afterwards was invisible to `_vacate_checkout`'s scan — which read the invoking copy — and retargeting another binding out of the shared checkout dropped the new binding's record; the next cone union then removed its materialization and left its consumer link dangling. The vacate scan — and the `(moved with …)` sibling listing — now read the manifest of the root that owns the checkout.
- `gf worktree add` now reports a failed rollback instead of hiding it: when a post-add failure triggered `git worktree remove --force` and that removal itself failed — a locked worktree needs the force doubled, or an fs error — the error output named only the original failure and left the registered orphan to confuse the retry; the removal now retries with `--force --force`, and when it still fails the die message names the orphaned worktree and the exact recovery command.
- A torn checkout state file no longer crashes every command that reads it: `save_checkout` truncated the state file in place, so a kill mid-write or a crash left invalid TOML and `tomllib` raised an uncaught `TOMLDecodeError` traceback on later `gf` runs that load that checkout's state; the write is now atomic — temp file plus `os.replace`, the same pattern `cmd_rm` uses for `gf.toml` — and a corrupt state file dies with a clean `gf:` message naming the file instead of a traceback.
- A relative local path whose first segment contains a dot is no longer rewritten to `https://`: `gf clone upx.git/docs/api api` expanded the conventional `<repo>.git/<subdir>` spelling as bare-host shorthand and fetched a bogus host; the expansion now applies only when neither the first segment nor the spelled path exists under the owning anchor — `./dir/...` or an absolute path was always a workaround, and `https://`/`git@` spellings are unchanged.
- A failed store creation's rollback no longer removes a store another invocation populated: `_remove_repo_store` ran unconditionally on the caller's `store_created` snapshot, so a losing invocation could delete `store/worktrees/<key>` records a concurrent join had just committed — wedging the winner's binding against the no-rebuild refusal; the remover now keeps any store that holds worktree records.
- An unreadable, malformed, or wrongly-shaped `gf.toml`/`gf.local.toml` now dies with a clean `gf:` error naming the file — and, for shape errors, the offending `git_folder[i]` entry and git-folder name — instead of a Python traceback: `read_manifest`/`read_local_overrides` wrap `OSError` and `TOMLDecodeError` into `GitFoldersError`, a `_validate_manifest` shape pass requires `git_folder`/`git_folder_override` to be lists of tables with string `name`/`url`/`ref`/`path` fields, and `main()` catches `GitFoldersError` so a failure that escapes a command exits with its deterministic code rather than crashing.
- An untrusted manifest `path` can no longer aim `gf` at files outside the parent — and the check fails CLOSED: `path` is validated when `gf.toml` is read (non-empty, relative, and normalized not `.`, `..`, or `../`-leading, with no `.gf` or `.git` segment), so a hostile manifest blocks every command including `gf rm` — unregistering around the bad entry is not a workaround; fix or restore the file first. Behind it, every write site that follows links now verifies realpath containment: the consumer link a `clone`/`pull` creates or retargets must sit lexically under its owning root with its parent's realpath inside the root and outside `.gf` and `.git`; `gf worktree add` refuses a child path whose parent resolves outside the new worktree (a committed mid-path symlink like `vendor -> /abs` no longer lets `worktree add -f` unlink outside files); `gf worktree remove` skips a leaf whose parent realpath escapes the worktree (the remove proceeds; the outside file is untouched); and `gf pull` refuses a consumer path that resolves outside the root that owns it, with the same refusal inside the child-creation and placeholder-strip layers.
- A consumer path that resolves inside `.gf` storage can never bind a whole-repo child: `gf init` on a path resolving into `.gf` — including a link into a store checkout, recordless or not — is refused instead of planting a `.gf` gitdir inside the store and then dying `did not create the expected worktree record` on every later run; `gf clone` and the `gf pull` child-creation path get the same refusal for a store-checkout or `.gf`-resolving child. A subfolder binding is unaffected — its consumer path legitimately resolves into `.gf/wt`.
- Every `gf.toml` write is now atomic and never writes through a `gf.toml` symlink: `write_manifest` uses the same `mkstemp`-plus-`os.replace` pattern `gf rm` and the checkout-state writer already used — a `gf.toml` that is itself a symlink is swapped for the regular file rather than followed — and `gf rm`'s inline write now delegates to the shared implementation.
- `gf pull` no longer un-materializes a live sibling binding when the checkout's owning manifest cannot be read: when the `gf.toml` of the root that owns the checkout is missing, unreadable, or corrupt, the vacated checkout's recorded `bindings`/`binding_urls` are left untouched instead of being pruned from a guessed scan, and the `(moved with …)` sibling list degrades to empty rather than aborting the pull — previously an unreadable owning manifest dropped a live binding's record and the next cone union removed its materialization.
- A dangling symlink at a consumer path is occupancy, not a traceback: `gf clone <url> <dangling-link>` and `gf init <dangling-link>` now die with a clean refusal instead of a `FileExistsError` traceback — a path that exists only as a link to nowhere is not empty space, and the link is preserved rather than removed as `gf`-created state. A link to a plain file is likewise refused with `not a directory` instead of crashing at `iterdir`, while a link to a real directory still binds through the link as before; `gf pull`'s whole-repo update path applies the same refusal to an unresolvable link (a self-referential one no longer tracebacks — an ordinary dangling consumer link is simply re-created as before).
- A failed `gf worktree add` rollback now reports the worktree's true state instead of always claiming an orphan: when even the `--force --force` removal reports failure, `gf` re-lists the worktree registration — a worktree that is actually gone gets only the original error (no phantom orphan), a worktree still registered but whose path is gone names `git worktree prune` as the remedy, and one still on disk names `git worktree remove --force <path>` as before.
- `gf pull` no longer misses a pinned `tag`/`commit` ref on the fetch that creates a repo store: `pull` created the store without passing the binding's ref, so a tag's `+refs/tags/<ref>:refs/tags/<ref>` coverage line was appended by the per-binding pass only after the one creating fetch had already run — the pin never landed and the first pull of a tag-pinned subfolder binding died `could not resolve ref '<ref>'`. `pull` now resolves each selected binding's effective ref before store creation and covers a non-branch ref inside the create step — the same `_ensure_pinned_ref`-before-the-initial-fetch mechanism `gf clone`'s create arm already used — so a needed tag's line lands in the creating fetch and a needed commit sha keeps its own `git fetch origin <sha>`; a retry after a pre-fix failure can leave a duplicated `+refs/tags/<ref>` line in the store's config, benign residue `gf` never rewrites or removes.
- `gf init` can no longer record a consumer `path` containing a `.gf` segment: `gf init sub/.gf/x` slipped past every refusal — the `.gf` sits mid-path, where the `parent/.gf` containment check never looked — planted a real gitdir at `sub/.gf/x/.gf/git`, and wrote `path = "sub/.gf/x"` into `gf.toml`, which read-validation then refused on every subsequent command (`reaches inside gf-managed storage`), a permanent wedge until the file was hand-edited; init now applies the reader's own lexical `.gf`-segment predicate to the recorded `path` before any side effect, and the child-creation layer (`init_git_folder`) carries the `in_gf_tree` `.gf`-interior refusal `init_child`/`update_child` already enforce, so init can never write a binding the manifest reader rejects.
- A filesystem `OSError` — a permission denial, a read-only mount, a path gone mid-command — no longer escapes the `gf:` envelope as a raw Python traceback: the consumer-link unlink/rmdir, `remove_child`'s link unlink and `.gf/git` move plus `.gf` rmtree, checkout-state reads and writes, and the `gf.toml` temp-write/replace each wrap `OSError` into `GitFoldersError`/`ValidationError` naming the operation and path — the caller's `folder_error` adds the git-folder name — and `main()` catches a residual `OSError` as a last resort for sites a sweep cannot enumerate, so every filesystem failure exits with the deterministic code; `KeyboardInterrupt`, `SystemExit`, and deliberate best-effort swallows stay untouched.
- A committed mid-path symlink can no longer aim `gf pull`'s storage writes outside the parent: a binding's owning root was adopted from ANY `*/.gf/wt/<repo-key>/<checkout-key>`-shaped ancestor of its consumer path's realpath with no legitimacy check — and `os.path.realpath` resolves a nonexistent path lexically, so the shape never had to exist — so `sub -> /outside/.gf/wt/X/master` committed in the tree plus `path = "sub/master/libs/api"` made `gf pull` create the repo store, the checkout, the per-checkout state, and the consumer links under `/outside`. `owning_root` now returns the derived root only when it proves real — a `.git` entry at that root (a directory, gitfile, or symlink; `.git` is never committed content, so the marker cannot be forged) or a `HEAD` in the matching `<root>/.gf/repos/<repo-key>/git` store — and an unproven shape falls through to `binding_root` then the invoking root, where the existing consumer-path routing refusal stops the pull before any fetch or write; `binding_root`'s marker test likewise refuses an ancestor inside a `.gf` tree, so a forged shape cannot claim the anchor off a `gf.toml` materialized inside one.
- A consumer link placed under a committed mid-path symlink no longer dangles: its relative target was computed against the spelled parent directory while the symlink was written at the realpath'd position, so `sub -> deep/nested/a` plus `path = "sub/x"` produced `deep/nested/a/x -> ../.gf/wt/...` resolving to `deep/nested/.gf/wt/...` — a link `gf status` showed as a phantom checkout (`api <url> []`: no porcelain lines, an empty branch marker), `gf rm` refused as a symlinked child it could not own, and whose `.gf/wt`-shaped dangling target could be adopted as an owning root. The relative target is now anchored at the link parent's realpath at both writing sites — the clone/pull create-retarget site resolves the target itself as well, while `gf worktree add` keeps the spelled source consumer path as its target so a source retarget still propagates link to link.
- `gf worktree add` now rolls the new worktree back on any post-add failure, not just `gf` and OS errors: the rollback catch covered only `GitFoldersError` and `OSError`, so copying a non-UTF-8 `gf.local.toml` (`UnicodeDecodeError` out of `read_text`) — or any other unexpected exception — escaped with a traceback and left the `git worktree add` registration behind, blocking the retry on the existing directory; the catch is now `Exception`, the contract every other rollback site already used, while `KeyboardInterrupt` and `SystemExit` still propagate.
- A non-UTF-8 `gf.toml`, `gf.local.toml`, or checkout `.state` file no longer escapes the `gf:` envelope as a traceback: `tomllib` decodes the file itself, so undecodable bytes raise `UnicodeDecodeError` — a `ValueError`, not a `TOMLDecodeError` — which slipped every envelope: a bad `gf.toml` tracebacked every command through `_resolve`, and a non-UTF-8 `gf.local.toml` or checkout `.state` crashed the commands that read them. `UnicodeDecodeError` is now caught alongside `TOMLDecodeError` at `read_manifest`, `read_local_overrides`, and `load_checkout`, and added to the two degrade-on-unreadable-manifest tuples in `shelf` and the `_get_version` `pyproject.toml` probe — an undecodable file dies as a clean `gf:` error naming it.
- `gf worktree add` now refuses a `<path>` that resolves at or inside ANY `.gf` directory, not just the parent's own `.gf` storage: the pre-add guard tested only `is_relative_to(parent/.gf)`, so `gf worktree add sub/.gf/w2` in a parent with no bindings landed a registered worktree inside a `.gf`-named subtree; the guard now applies the layout's `in_gf_tree` check — an exact `.gf` segment anywhere in the resolved path, covering the parent's `.gf`, another root's `.gf`, and any `.gf`-named tree in between — and still refuses before `git worktree add` runs.
- Consumer paths carrying a `.git` segment are refused everywhere: a committed manifest could spell `path = ".git/hooks/post-checkout"`, and a `gf pull` then placed the consumer link inside the parent's `.git` — a hook-named entry under `.git/hooks` runs on the next `git` operation, so the path was code execution through committed content. Manifest read-validation now rejects a `path` containing a `.git` part (failing closed like the `.gf` rule — a hostile manifest blocks every command, `gf rm` included), and a new `layout.in_git_tree` realpath predicate backs it at every write and guard site — `ensure_consumer_link`, the `init_child`/`update_child`/`init_git_folder` child-creation layer, the `clone`/`init`/`worktree add` path guards, the `worktree add` link placement, and the `worktree remove` symlink scan — so neither a spelled operand nor a mid-path link can land a `gf` write inside a `.git` tree.
- A `.gf` directory that is itself a symlink no longer redirects `gf`'s storage writes: `.gf` is committable content (the `.gitignore` recommendation is advice, not enforcement), so a `parent/.gf -> /outside` link sent the repo store's `init --bare`, the checkout's `worktree add`, a child's `.gf/git` creation, and teardown `rmtree`s through the link and outside the workspace. Every `.gf`-rooted storage path `gf` populates must now resolve to itself — the `.gf`/`repos`/`wt`/`git` components appended below a realpath'd anchor must be literal; a whole-repo child's own leaf may still be a link — checked at the write site (`ensure_repo_store`, `ensure_checkout`, `_init_child_gitdir`, `init_git_folder`, and the `pull_shared_bindings` store guard for an existing store), and `_remove_repo_store`/`_remove_checkout` skip the `rmtree` when the target resolves through a link, so cleanup can leave storage behind but never deletes a linked tree. Until the every-operation check below, that predicate ran only at those write sites — discovery, `ls`/`status`, and every established-child operation still resolved through the swapped link; reads now degrade to `missing`/`?` instead of resolving hostile storage.
- Ambient `GIT_*` variables can no longer retarget or corrupt the `git` processes `gf` spawns: an inherited `GIT_DIR` silently rebound `git worktree list` to a foreign repository, an inherited `GIT_INDEX_FILE` made pulls write a caller-chosen index, and injected `GIT_CONFIG_*` pairs (for example `protocol.file.allow=never`) reached every child `git`. `gf` now scrubs the ambient `GIT_*` set — repository pointers, index/object paths, quarantine and graft files, ceiling/discovery switches, `GIT_EXEC_PATH`, config-injection pairs, and pathspec-mode flags — from every spawned `git` before applying its own `GIT_DIR`/`GIT_WORK_TREE` overlays; `gf sh` and the `git`/`diff`/`log` passthroughs are scrubbed the same way, while `GIT_CONFIG_GLOBAL`, identity, and transport variables still reach the child.
- A failed subfolder join's rollback no longer removes a checkout the invocation did not create: the join arm snapshotted `_checkout_record_valid` before `ensure_checkout` ran, so a checkout materialized in between — a concurrent invocation's `worktree add` — was served as an existing checkout yet still torn down by `_remove_checkout` when a later link or state step failed; `ensure_checkout` now reports whether it created the checkout, and the join arm removes only that case, so a foreign or pre-existing checkout survives a failed join.
- `gf clone`/`init` of a spelled `sub/.gf/x` or `sub/.git/x` path now refuses before binding: the spelled-path segment check ran inside the manifest record step but the child-creation layer's already-a-git-folder early return fired first, so cloning onto an existing child that had been moved under a `.gf`-named (or `.git`-named) directory silently recorded a `path` the reader then refused forever — `gf ls`, `status`, and `rm` all wedged on the segment refusal (`reaches inside gf-managed storage`/`repository metadata`) until a hand-edit. The `.gf`/`.git` segment refusal now runs on `binding_path` ahead of the early return, exact path-part matching only (a `x.gf` name is unaffected), and nothing is written or recorded.
- `git` output that is not valid UTF-8 no longer escapes as a traceback: captured subprocess output was decoded strictly while streamed output replaced bad bytes, so a ref name carrying raw `0xff` crashed `gf` with `UnicodeDecodeError` before the real error message could print. Capture mode now decodes with replacement, matching stream mode — the malformed bytes surface as U+FFFD inside the `gf:` error.
- A corrupt checkout `gitdir` record no longer tracebacks: `_checkout_record_valid` read the `<store>/worktrees/<checkout-key>/gitdir` file with a bare `read_text`, so a non-UTF-8 or unreadable record crashed every command that validated the checkout — the first `gf pull` after the corruption died on `UnicodeDecodeError`. The record now reads under the same `(OSError, ValueError)` guard as other state reads: an unreadable record is simply an invalid record — the checkout is recreated when its path is free, and refused with `refusing to rebuild over existing files` when a populated checkout still occupies it.
- A repository whose default branch is `feature/main`-style — a `/` in the branch name — now clones and pulls on a whole-repo binding: `latest` resolution derived the branch name from the LAST path segment of the `refs/remotes/origin/HEAD` target, so `refs/remotes/origin/feature/main` yielded `main` and the `checkout -B main origin/main` died on a nonexistent ref (every later `latest` resolution failed the same way); the name is now derived by stripping the `refs/remotes/origin/` prefix — `feature/main` — matching how the store-side default-branch readers already derived it.
- `gf -C <rel>` no longer loses the operand's logical spelling: `PWD` was recomputed from the operand AFTER `os.chdir`, so `gf -C one` recorded `<one>/one` — a path that names nothing — and the logical cwd fell back to the physical directory; a `-C` operand spelling a symlink therefore lost its spelled path, and the lexical consumer-path tiebreak that selects one binding among aliases on one map could not see it. `PWD` is now computed from the spelled operand before the `chdir`, so `gf -C one pull` keeps the same logical cwd as `cd one && gf pull`.
- `gf pull --autostash` no longer orphans the user's stash when the post-stash `origin` update fails: the `git remote set-url` step sat outside the `try` that restores the stash, so a failed URL update exited with the `gf autostash` entry still in `git stash list` and the worktree still clean. The origin update now runs inside that `try`, so its failure pops the stash and the user's dirt returns like any other update failure.
- `gf worktree remove` now refuses whenever the current working directory is inside the target worktree, not only when it equals it: the guard tested exact equality, so `cd <worktree>/sub && gf worktree remove <worktree>` removed the caller's own cwd out from under it. The refusal — `<path> contains the current working directory; refusing to remove it` — uses the logical cwd and covers the worktree itself and every descendant, while removal from outside the target is unchanged.
- Local `/path/repo` and `/path/repo.git` bindings no longer collapse onto one repo key: repository-key normalization stripped a trailing `.git` unconditionally, so two different local directories were served by a single store — the second binding fetched the first's objects and linked the wrong bytes. A `.git` suffix is now significant only for local paths (remote spellings keep the historical alias), so the two directories get separate stores, links, and content; an existing collapsed store migrates on the next pull, which may leave the old store and checkout — and any uncommitted work in it — behind as residual storage.
- Deferred this round: concurrent `gf clone`/`init`/`rm` invocations can still lose a `gf.toml` update entirely — each invocation snapshots the manifest it read, so the last writer wins and a completed clone's `git_folder` entry can be silently dropped, leaving a fully materialized store, checkout, and link that `gf ls`/`rm` cannot see. A real fix needs a manifest lock protocol; the residual and its recovery (re-add the binding — the orphaned storage rejoins in place) are recorded under GF-TRB-11 in the troubleshooting doc.
- The ambient `GIT_*` scrub no longer leaves config-source and command-path channels open to spawned `git`: `GIT_CONFIG`, `GIT_CONFIG_GLOBAL`, and `GIT_CONFIG_SYSTEM` pointed every `git` `gf` spawns at caller-chosen config files — a swapped `GIT_CONFIG_GLOBAL` could write `core.hooksPath` or `protocol.file.allow=never` into clone/pull/rm — `GIT_TEMPLATE_DIR` seeded `init` from a caller-chosen template, `GIT_DEFAULT_HASH`/`GIT_DEFAULT_INITIAL_BRANCH_NAME` rewrote repository defaults, `GIT_INDEX_VERSION`/`GIT_SHALLOW_FILE`/`GIT_NO_REPLACE_OBJECTS` rewrote index and object semantics, `GIT_SSH`/`GIT_EXTERNAL_DIFF` executed caller-chosen commands, and the `GIT_TEST_*` family leaked test-harness internals. `clean_environ`'s blocklist now covers all of them plus the `GIT_TEST_` prefix; `GIT_CONFIG_NOSYSTEM`, author/committer identity, and the remaining transport variables still pass through.
- An upstream that tracks `.gf` at its tree root can no longer plant gf-managed plumbing: a committed `.gf` entry — blob, tree, symlink, or gitlink — would materialize where `gf` anchors a child's own metadata, so it is refused before the tree materializes (a nested `sub/.gf` does not collide with the anchor and is unaffected); every `git` operation `gf` itself runs against gf-managed gitdirs now runs with `core.hooksPath=/dev/null` so a committed hook cannot execute during clone/pull/rm — the `gf sh`/`gf git`/`gf diff`/`gf log` passthroughs keep normal hook resolution, so a user's own hooks still run — and `gf pull` refuses an existing repo store whose `remote.origin.url` does not match the binding's recorded resolution instead of fetching from a rewritten origin.
- A `.gf` swapped for a symlink on an established child no longer carries any `gf` operation through the link: the resolve-to-self check — `storage_is_real` on `.gf`-rooted storage components and the two-sided `realpath(gitdir) == realpath(child)/.gf/git` comparison — previously ran only at storage write sites, so an established child's update/`pull`, `rm`, and passthroughs still operated through the hostile link; the check now gates every operation on an established binding — `gf pull` and the update paths refuse, `gf rm` refuses, and `gf sh`/`gf git`/`gf diff`/`gf log` refuse — while read paths degrade instead of dying: `gf status`, `gf ls`, and drift report the binding as `missing`/`?`, so discovery and listing keep working and no `git` process touches the swapped storage.
- `gf worktree add` no longer copies manifest content through a source link: the source-side gate was `src.exists()`, which follows links, so a `gf.toml`/`gf.local.toml` in the source worktree that was itself a symlink — or a special file — had its target's bytes read and planted at the manifest path inside the new worktree; the copy now propagates only a regular non-symlink source file — a link or special source is skipped — while the destination side is unchanged: a checked-out link at the destination is still unlinked and replaced, and a non-regular non-link destination still refuses and rolls the worktree back.
- `gf pull --force` is gone: `gf` offers no flag that updates over uncommitted work, so a dirty child refuses with exit `3` naming the dirty state and the recoveries — commit or stash first, or pull with `--autostash` — and passing `--force` now dies with a message explaining the removal. `--autostash` keeps the semantics but restores with `git stash pop --index`, so the staged/unstaged partition survives, and the stash is restored after a successful update and after every failure that follows the stash — a failed `origin` URL update included; a pop that conflicts or fails leaves the named `gf autostash` entry in the stash list and reports the manual recovery instead of dropping it.
- `gf pull` can no longer move or discard a local branch: the update used `checkout -B`/`checkout -f`, which recreated the tracking branch at the remote tip and overwrote the worktree — local commits were silently stranded. A branch ref now creates the local tracking branch at `origin/<branch>` only when it does not exist (`checkout -b`), attaches to an existing one (`checkout <branch>`), and integrates `git merge --ff-only origin/<branch>` — a strictly-behind branch advances, an up-to-date one is a no-op, a strictly-ahead one keeps its commits untouched, and a diverged one refuses with the truthful ahead/behind counts plus the recoveries (`gf pull --rebase` runs `git rebase origin/<branch>` on explicit request). A tag/commit ref checks out the detached resolved SHA as before, and a checkout in a merge, rebase, cherry-pick, or revert refuses to stack another operation on it.
- A pull that would strand the outgoing `HEAD` now leaves it reachable before anything moves: `_apply_ref` writes `refs/worktree/gf-retained` to the outgoing `HEAD` — per-worktree under a repo store, in the child's own `.gf/git` for a whole-repo binding, so the `.gf` → `.git` move carries it — and a failed write refuses the checkout rather than leaving the outgoing commits reachable only through the reflog.
- `gf`'s fetches no longer move user-owned refs: every `gf`-issued `git fetch` now runs `--no-tags`, tag coverage is appended as the non-forced `refs/tags/<ref>:refs/tags/<ref>` (a moved upstream tag is a refusal, not something `gf` silently tracks), and a pre-existing `remote.origin.fetch` line carrying `+` into a destination outside `refs/remotes/origin/*` — `refs/heads/*`, `refs/tags/*` — refuses before any fetch or write runs against that store or child gitdir, naming the offending line; `gf` never rewrites or removes an existing refspec.
- A checkout pinned to a ref the store's live refspecs never covered — a tag that only an unfetched branch names under `--no-tags`, a deleted upstream's leftover — now resolves instead of dying `could not resolve ref`: `ensure_checkout` appends the same non-forced pin coverage the clone and pull seams write, fetches once, and resolves again; a ref upstream does not advertise keeps the resolve's clean error.
- A shared checkout directory deleted out from under its surviving worktree record heals on the next `gf pull`: the record's arm recreates the empty directory and materializes the recorded index back into it — a directory `gf` itself just `mkdir`'d holds no user work — so the dangling consumer link resolves again without any flag; a populated checkout path whose record is missing still refuses, never rebuilt over.
- `gf status --remote` now reports the truthful history relation instead of a same/different guess: drift classifies `HEAD` against the locally-resolved ref by `git rev-list --left-right --count HEAD...<sha>` — `clean`, `ahead` (local commits the resolved SHA lacks), `behind`, `diverged`, or `missing` — with a `-dirty` suffix when the worktree is dirty (`local-dirty` for the matching-`HEAD` case, `missing` never suffixed); an unborn `HEAD` reports `behind` when the ref resolves, an unresolvable ref still dies with the deterministic non-zero envelope, and the computation stays local-only — no fetch.

### Correctness and consistency

- All commands use a centralized `_resolve(cwd)` helper for manifest and parent discovery.
- `gf ls` is global; `gf status`, `pull`, and `rm` remain context-aware.
- `gf rm` only unregisters the git-folder and preserves the worktree.
- `gf status` and `gf pull` return quiet success when `gf.toml` is missing.
- Documentation consistency cleanup: the architecture `drift` entry now matches local-only drift, the spec's stale `--ref` flag, superseded-scheme narration, and "two subfolders" example are corrected, the `.gf` grep witness in the constraints actually recurses, the testing plan's layout table covers every test file, and the architecture seam entries carry their owner, direction, and test-seam fields.
